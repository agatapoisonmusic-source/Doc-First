# Промт-каркас системного аналитика

Основано на анализе 230 промтов из 23 сессий (21.10–11.11.2026).
Главная потеря — не ясность цели, а **контракт результата**: формат задавался после, отсюда циклы «слишком много лишнего → верни как было».

## Базовый каркас (5 строк)

```
Роль:      <кто смотрит: SA / backend / frontend / тестировщик / редактор>
Контекст:  <страницы, файлы, что НЕ читать, что вне скоупа>
Задача:    <одно предложение + 3–7 пунктов>
Выход:     <формат: разделы/таблица/длина, ссылка на шаблон>
Готово когда: <проверяемые критерии + стоп-условие>
```

Правила:
- **Одна роль на один промт.** Девять ролей сразу размывают фокус.
- **Стоп-условие обязательно.** «Публикуй» — отдельная команда, не следствие.
- **Скоуп через отрицание.** «BDUI вне скоупа», «Портфель — не наша фича».
- **Ответы списком по номерам.** Самый дешёвый и однозначный формат подтверждения.

## Замена «Продолжай»

| Плохо | Почему | Как |
|---|---|---|
| `Продолжай` | агент сам выбирает шаг, часто не тот; лишние вызовы | `Следующий шаг: X. Ограничения: Y. Стоп после Z.` |
| `Внеси` | непонятно, что именно и куда | `Внеси п.2 и 4 в раздел «Опции». Публикуй только после моего «ок».` |
| `Короче` | агент сокращает случайно | `Сожми до 1 экрана: оставь решение, опции, риски. Убери историю и примеры.` |

## Шаблон 1. Research-страница

```
Роль: системный аналитик, автор research.
Контекст: задача FUJI-XXXX; страницы: <ссылки>. Шаблон: <ссылка на Шаблон Research>.
Читать только разделы про поиск и рынки, остальное игнорировать.
Задача:
1. AS IS: как работает сейчас (с источниками).
2. Метрики и потребители контракта.
3. 2–3 опции: решение, плюсы, минусы, зона доработки.
4. Рекомендация + почему выбранная, почему не остальные.
5. Риски и открытые вопросы.
Выход: строго по шаблону, без моноширинного текста, ≤ 3 экрана.
Готово когда: у каждого вывода есть источник; спорное — в «Открытые вопросы», а не додумано.
Стоп: черновик в чат, публикация — после подтверждения.
```

## Шаблон 2. Постановка на Front

```
Роль: системный аналитик, пишет для frontend-разработчика.
Контекст: FRONT-страница <ссылка>, Premiddle <ссылка>. Платформы: Android, iOS, Web (АИО).
Скоуп: <что входит>. Вне скоупа: <что не входит>.
Задача: заполнить разделы: поведение, входные данные и контракт, состояния экрана
(пусто/загрузка/ошибка/частичный ответ), corner cases, ФТ, метрики, DoD.
Выход: текст для вставки, без моноширинного, ≤ 1,5 экрана.
Готово когда: каждый corner case имеет ожидаемое поведение;
каждое требование проверяемо; расхождения с Premiddle перечислены явно.
Стоп: не публиковать, отдать текст.
```

## Шаблон 3. Задача в Jira

```
Роль: аналитик, пишет задачу для трёх платформ (Android / iOS / Web).
Контекст: описание в Confluence <ссылка>.
Задача: заголовок + 3–5 пунктов «что сделать» + ссылка на документацию.
Выход: ≤ 800 символов, без деталей — детали в Confluence.
Готово когда: понятно, о чём задача, без открытия документа.
```

## Шаблон 4. Вопросы бизнесу

```
Роль: бизнес-аналитик, готовит интервью.
Контекст: <материалы>, согласованные термины: <список>.
Задача: вопросы, которые закрывают неопределённость: потребность, критерии готовности,
границы понятий, корнер-кейсы. Для каждого — почему спрашиваем.
Выход: таблица «№ | вопрос | варианты ответа | зачем». Без деления на разделы.
Готово когда: нет вопросов, на которые ответ уже есть в документации.
```

## Шаблон 5. Правка существующего документа

```
Роль: технический редактор.
Задача: точечные правки в <страница>. Не переписывать целиком.
Запреты: не менять существующие оценки и цифры; не удалять разделы;
не использовать моноширинный текст; не додумывать за заказчика.
Выход: diff по разделам (было → стало), ≤ 10 правок за итерацию.
Стоп: применить только после «применяй».
```

## Чек-лист перед отправкой промта

- [ ] Указана роль и что вне скоупа
- [ ] Есть ссылка на шаблон или перечислены разделы
- [ ] Задан лимит объёма
- [ ] Описано, что считается «готово»
- [ ] Есть стоп-условие для необратимых действий
- [ ] Сырьё лежит файлом, а не вставлено в промт
