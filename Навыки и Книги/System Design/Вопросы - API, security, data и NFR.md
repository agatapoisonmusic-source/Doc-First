# Вопросы - API, security, data и NFR

## Как бы ты объяснил разницу между REST и SOAP? И в каких случаях SOAP до сих пор может быть оправдан?

REST - это архитектурный стиль взаимодействия, обычно поверх HTTP. Он ориентирован на ресурсы, использует HTTP methods - GET, POST, PUT, DELETE - и чаще всего JSON. REST проще, легче, лучше подходит для web/mobile и современных микросервисов.

SOAP - это protocol-based подход. Он использует XML-сообщения и строгий контракт через WSDL/XSD. SOAP более тяжелый, но дает стандартизированные enterprise-возможности:

- WS-Security
- message signing
- encryption
- transaction support
- strict contract validation

REST чаще выбирают для современных API и микросервисов. SOAP до сих пор оправдан:

- в банках и enterprise
- при интеграции с legacy-системами
- где нужны строгие контракты
- сложная security-модель
- формализованный документооборот и compliance

## Что такое API Gateway и какие задачи он обычно решает в микросервисной архитектуре?

API Gateway - это единая точка входа для клиентов в микросервисную систему.

Он решает несколько задач:

- routing - маршрутизация запросов к нужным сервисам
- authentication/authorization
- rate limiting
- SSL termination
- request/response transformation
- aggregation нескольких backend-вызовов
- logging, tracing, metrics
- versioning API

Gateway позволяет клиентам работать с единым API, не зная внутренней структуры микросервисов. Это уменьшает связанность frontend и backend.

Также через gateway удобно реализовывать безопасность внешнего контура и централизованные политики доступа.

## Чем authentication - аутентификация - отличается от authorization - авторизации? И как это обычно реализуется в современных системах?

Authentication - аутентификация - отвечает на вопрос "кто ты?". Система проверяет личность пользователя: логин/пароль, MFA, SSO, OAuth-provider и так далее.

Authorization - авторизация - отвечает на вопрос "что тебе разрешено?". После успешной аутентификации система определяет, к каким ресурсам и операциям пользователь имеет доступ.

В современных системах authentication часто выносится в отдельный identity provider, например Keycloak. После успешного логина пользователь получает token - например JWT - который содержит identity и claims пользователя.

Дальше backend или API Gateway проверяют токен и применяют правила authorization:

- RBAC - доступ по ролям
- ABAC - доступ по атрибутам
- data scope - область видимости данных

## Что такое JWT token? Какие у него плюсы и минусы?

JWT - JSON Web Token - это signed token, который содержит claims о пользователе: userId, roles, scopes, expiration time и другие атрибуты.

После успешной аутентификации identity provider, например Keycloak, выдает JWT. Клиент отправляет его в каждом запросе, а backend проверяет подпись токена и использует claims для authorization.

Основной плюс JWT - stateless authentication. Backend не обязан хранить server-side session, что хорошо масштабируется в микросервисах.

Минусы:

- токен обычно не зашифрован, а только подписан, поэтому payload можно прочитать
- сложно мгновенно revoke токен
- большие JWT увеличивают размер запросов
- нужно аккуратно работать с expiration и refresh token

## Что такое race condition - состояние гонки? Приведи пример в банковской или highload системе.

Race condition - состояние гонки - возникает, когда несколько процессов или транзакций одновременно работают с одним ресурсом, и результат зависит от порядка их выполнения.

Например, два запроса одновременно читают баланс кошелька 1000 рублей и оба пытаются списать по 700. Если операции не синхронизированы, оба могут успешно пройти проверку и итоговый баланс станет некорректным.

В highload и distributed systems race condition особенно опасны, потому что запросы выполняются параллельно на разных инстансах и сервисах.

## Что такое CAP theorem - теорема CAP - простыми словами?

CAP theorem говорит, что в распределенной системе при сетевом разделении - network partition - невозможно одновременно обеспечить:

- strict consistency
- full availability
- partition tolerance

Поскольку network partition в распределенных системах неизбежен, обычно приходится выбирать компромисс между consistency и availability.

Например:

- банковские операции чаще ближе к CP - consistency + partition tolerance
- многие highload/web системы ближе к AP - availability + partition tolerance и используют eventual consistency

Лучше: отказать чем: показать разные балансы

## Чем SQL БД принципиально отличаются от NoSQL? Когда бы ты выбрал NoSQL решение?

SQL БД - это реляционные системы со строгой схемой, ACID-транзакциями, relational constraints и возможностью сложных JOIN-запросов. Они хорошо подходят для систем, где важны консистентность данных, транзакционность и связи между сущностями. Например: деньги, заказы, заявки, учетные системы.

NoSQL - это широкий класс нереляционных хранилищ:

- key-value
- document
- column-family
- graph databases

Они обычно лучше подходят для:

- highload
- горизонтального масштабирования
- гибкой схемы
- event/log data
- больших объемов semi-structured data

NoSQL я бы выбирал, когда:

- структура данных часто меняется
- нет сложных relational queries
- нужна высокая скорость записи
- нужен distributed scaling
- eventual consistency допустима

## Что такое CQRS и зачем разделять read и write модели?

CQRS - Command Query Responsibility Segregation - это паттерн разделения моделей чтения и записи.

Основная идея в том, что требования к write operations и read operations часто разные:

- запись требует консистентности, нормализации и бизнес-валидаций
- чтение требует быстрых запросов, агрегаций и удобной структуры данных

Поэтому write model проектируют под корректное изменение состояния, а read model - под эффективное чтение. Read model часто денормализована и может храниться отдельно:

- в read replica
- cache
- Elasticsearch
- materialized view

Между write и read model обычно есть asynchronous synchronization, поэтому CQRS часто связан с eventual consistency.

CQRS полезен в highload systems, где чтений значительно больше, чем записей, и сложные JOIN/aggregation начинают тормозить систему.

## Представь, что бизнес говорит: "Система иногда показывает старые статусы заявок 5-10 секунд". Как ты будешь выяснять - это баг или допустимая eventual consistency?

Я бы сначала проверил, зафиксировано ли требование к свежести данных: например, статус должен обновляться не позднее 5 секунд после изменения. Если такого требования нет, нужно согласовать SLA/SLO на актуальность статуса.

Затем я бы выяснил источник статуса: где source of truth, как статус попадает в read model, есть ли кэш, очередь, реплика, событие.

Если архитектурно используется eventual consistency и задержка укладывается в согласованный SLA - это не баг, а свойство системы. Если задержка превышает SLA или статус критичен для дальнейшего действия пользователя - это дефект или архитектурный риск.

## Что такое NFR - нефункциональные требования? Приведи примеры NFR для личного кабинета партнера банка.

NFR - нефункциональные требования - описывают не то, что система делает, а как она должна это делать. Это требования к качественным характеристикам системы.

Для партнерского кабинета банка примеры NFR:

- performance - 95% запросов должны отвечать быстрее 2 секунд
- availability - доступность 99.95%
- scalability - система должна выдерживать рост до 100 тысяч партнеров
- security - MFA, audit log, encryption, RBAC
- reliability - отсутствие потери заявок и событий
- observability - логирование, tracing, мониторинг
- fault tolerance - система должна переживать отказ отдельного сервиса
- data freshness - статус заявки обновляется не позднее 10 секунд

NFR сильно влияют на архитектурные решения: выбор БД, очередей, кэширования, отказоустойчивости и интеграций.
